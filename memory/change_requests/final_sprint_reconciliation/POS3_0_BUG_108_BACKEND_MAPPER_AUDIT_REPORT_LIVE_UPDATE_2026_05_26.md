## 4. 🔴 I-5 Defect Detail

### Observed
```
loyalty_info = {
  "loyalty_discount": 237,
  "loyalty_points_used": 237,
  "loyalty_idempotency_key": None,   // ← should be "order_869016_loyalty"
  "updated_at": "2026-05-26 15:00:22"
}
```

### Expected (per Phase C contract)
```
loyalty_info.loyalty_idempotency_key = "order_869016_loyalty"
```
(or whatever deterministic shape the POS Backend / CRM team locked in
the Phase C contract freeze).

### Why this matters
- CRM `POST /pos/loyalty/redeem` (or whichever internal endpoint POS
  Backend hits) is keyed on `(user_id, idempotency_key)` for replay safety.
- With `idempotency_key = null`, a retry will be treated as a fresh
  redeem → **customer's loyalty balance may be debited twice** for the
  same order.
- POS Frontend deliberately does **not** generate this key (per
  `BUG108_FLAGS.js` line 38 comment and `loyaltyService.js`
  `buildRedeemIdempotencyKey` which is dead code under
  `loyaltyRedeemLive=false`). Generation is owned by POS Backend.

### Owner
**POS Backend team (Laravel).** Frontend has no work here.

### Recommended fix
1. POS Backend, in the order-commit handler, before calling CRM
   `/pos/loyalty/redeem`, set
   `loyalty_idempotency_key = 'order_' + order_id + '_loyalty'`
   when `used_loyalty_point > 0`.
2. Persist the key on the orders / loyalty_info row.
3. Reissue on idempotent replay.
4. Add a backend unit test asserting key is non-null whenever
   `used_loyalty_point > 0`.

### Severity
**P1 / blocker for the BUG-108 sprint close** (production risk of
double-deduct).

### Repro evidence
Order id `869016` on restaurant 689 (preprod).
