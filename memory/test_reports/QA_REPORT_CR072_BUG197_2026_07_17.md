## Findings

### FINDING 1 (BLOCKER): Recipe Write Endpoints Return 302 — BACKEND ISSUE

**Severity:** BLOCKER
**Classification:** BACKEND_BUG
**Affected:** Standard recipe update, sub-recipe update, addon recipe update, recipe store (create)
**NOT affected:** Recipe GET (works), Recipe DELETE (works)

**Evidence:**
- Same auth token works for GET + DELETE on recipe endpoints
- Same auth token works for ALL non-recipe write endpoints (wastage, vendor, purchase, ingredient)
- PUT returns 302 redirect, POST returns 405
- This means backend route is registered as POST but middleware redirects authenticated POST requests

**Root Cause Hypothesis:** Recipe write endpoints may require an additional permission, CSRF token, or have a feature flag that's disabled for this restaurant. The 302 redirect pattern (not 401/403) suggests middleware redirection, not auth rejection.

**FE Code Status:** CORRECT — `api.put()` is the right call based on the update pattern. The issue is backend won't accept ANY write method on recipe endpoints.

**Recommendation:** File BACKEND BRIEF. FE code for recipe CRUD should remain as-is (PUT for update, POST for store). Backend team needs to investigate why recipe write endpoints redirect.

### FINDING 2 (NOTE): Recipe API Response Field Names

**Severity:** NOTE
**Finding:** Recipe GET response uses `recipe_id` (not `id`), `serve_people` (not `serves_people`), and ingredient fields use `ingredient_id`/`ingredient_qty` (not `id`/`qty`). The FE transform (`recipeTransform.js`) correctly maps these — verified in `fromAPI.recipes()`.

### FINDING 3 (NOTE): Vendor Add Requires `vendor_name` Not `name`

**Severity:** NOTE
**Finding:** Vendor add endpoint requires `vendor_name` field. FE transform correctly sends `vendor_name: data.name`. Verified working.
