## Failures — Detailed

---

### FINDING 1 — BLOCKER: V1 Header overflows at 600×960

**Filed as:** BUG-565  
**Severity:** BLOCKER — core tablet layout broken at the smallest supported viewport

**What happens:** At 600×960 viewport (the minimum OD-537-01 support target), the header `pos-header` element overflows by **44px**:
- `scrollWidth = 588` vs `clientWidth = 544`

The tablet has sidebar-rail (56px), leaving 544px for the header. The header content wants 588px — 44px too wide.

**Measured content widths at 600px:**
- Sidebar rail: 56px
- Available for header: 544px
- Header offsetWidth: 520px but scrollWidth: 597px (inner content overflows)
- Overflow: **44px**

**Root cause hypothesis:** The left section div that wraps logo + filter button has `gap-4` (16px) spacing. At 544px total: filter button alone is ~138px wide, logo+gap+filter = ~(logo) + 16 + 138. The `flex-1` on the search container may not be shrinking properly at narrow widths — possible `min-w-0` missing on left section or a fixed-width element blocking flex shrink.

**Impact:** On a real 600px tablet, the Add button is pushed off-screen and users cannot add new orders. The entire purpose of CR-414 is broken at this width.

**Evidence:** V1 measurements — `scrollWidth=588, clientWidth=544, overflow_px=44`

---

### FINDING 2 — MAJOR: V7 Last status filter guard broken

**Filed as:** BUG-566  
**Severity:** MAJOR — user can deselect ALL status filters, leaving the dashboard showing 0 orders

**What happens:** In the tablet filter dropdown (Channel view), after deselecting all status filters except one, clicking the final active filter removes it. The `handleStatusToggle` guard `if (next.length === 0) return` is NOT preventing the last deselection.

**Steps to reproduce:**
1. 600×960 viewport, dashboard Channel view
2. Open tablet-filter-dropdown-btn
3. Deselect filters one by one until only 1 remains
4. Click the last remaining active filter
5. **Result:** Check mark disappears, 0 orders shown on dashboard

**Root cause hypothesis:** The guard exists in the pill's `handleStatusToggle` function. When called via the tablet dropdown button's `onClick`, it may be executing with a **stale closure** (state captured at the time the component rendered, before the previous deselects updated state). A rapid-click sequence in testing could expose a React batching issue. Alternatively, the filter's `onClick` in the tablet dropdown calls `handleStatusToggle(status.id)` correctly but the guard reads a stale version of `activeStatuses`.

**Impact:** Dashboard shows 0 orders. User is stuck with no way to restore the view (must reload page). Confusing and unusable.

### FINDING 3 — MINOR: V12 localStorage not updated on arrow click (spec conflict)

**Filed as:** NOTE only — spec conflict needs owner resolution before Bug Fix  
**Severity:** MINOR

**What happens:** Tapping `>` arrow on Dine-In at 600×960:
- Console shows `[Arrow] dineIn 2→3` ✅ (React state updates)
- `localStorage.getItem('mygenie_layout_table_view')` remains `null` ❌

**The conflict:** 
- Plan V12(b) test requirement: "localStorage key updates after arrow click"
- Code comment in `ChannelColumnsLayout.jsx` says: `// OD-414-02=A: maxColumns/localStorage untouched on tablet`

These two statements contradict each other. The code was intentionally written NOT to persist on tablet (OD-414-02=A said "arrows persist, rotate to desktop → applies"). But the QA test spec says it must persist.

**Owner decision needed:** Is V12(b) correct (persist on tablet) or is the code correct (don't persist on tablet)? This determines whether this is a code bug or a spec bug.
