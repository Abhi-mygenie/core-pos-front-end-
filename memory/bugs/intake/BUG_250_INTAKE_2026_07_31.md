## 1. One-Line Summary

Rider name and status are never displayed on aggregator order cards (Swiggy/Zomato) even when a rider is actively assigned — the card always shows "Awaiting Runner".

---

## 2. Observed Behaviour

On the Dashboard, aggregator delivery orders (Swiggy / Zomato) that have an active rider assigned via UrbanPiper show:

- Rider section renders with **"Awaiting Runner"** text
- No rider name displayed
- No rider phone displayed
- No status badge ("Assigned" / "Order Accepted") displayed

This is visible on `OrderCard.jsx` (dashboard column view) and `DeliveryCard.jsx`.

---

## 3. Expected Behaviour

When `rider_info` is present in the API response (from UrbanPiper aggregator endpoint), the order card should display:

- Rider name (e.g. "VEERJINDER SINGH")
- Rider phone (e.g. "9988190570")
- Appropriate status badge ("Assigned" or "Order Accepted") based on `f_order_status`

---

## 4. API Response Evidence

The aggregator orders endpoint (`GET aggregator order list`) returns `rider_info` correctly populated:

```json
{
  "rider_info": {
    "id": 186197119,
    "name": "VEERJINDER SINGH",
    "Phone": "9988190570",
    "Cahnel": "swiggy",
    "order_return_otp": null,
    "bag_return_otp": null
  },
  "order_details_order": {
    "rider_name": null,
    "rider_phone_number": null,
    "delivery_man_id": null
  }
}
```

Note: `order_details_order.rider_name` and `rider_phone_number` are `null` — rider data lives exclusively in the top-level `rider_info` object with non-standard casing (`Phone`, `Cahnel`).

## 5. Root Cause — Gap Analysis (5 Gaps)

### GAP-R1 — Critical: Field Name Mismatch `riderName` vs `rider`

| Location | Code |
|---|---|
| `aggregatorTransform.js:85` | emits `riderName: rider.name` |
| `OrderCard.jsx:912` | reads `order.rider` (not `order.riderName`) |
| `DeliveryCard.jsx:112` | reads `order.rider` (not `order.riderName`) |

`order.rider` is `undefined` for all aggregator orders → falls through to "Awaiting Runner".

`orderTransform.js:315` (POS path) correctly emits `rider:` from `delivery_man` object. Aggregator transform has no equivalent `rider:` key — it uses `riderName` instead, which is never read by any UI component.

### GAP-R2 — High: `riderStatus` Not Computed in `aggregatorTransform`

`OrderCard.jsx:922–939` renders two status badges:
```js
{order.riderStatus === 'riderAssigned' && <span>Assigned</span>}
{order.riderStatus === 'dispatched'    && <span>Order Accepted</span>}
```

`aggregatorTransform.js` never emits `riderStatus`. No derivation logic exists. Both badges are permanently invisible for aggregator orders.

### GAP-R3 — High: `deliveryManId` Not Mapped

`OrderCard.jsx:111`:
```js
const hasRiderAssigned = !!order.deliveryManId;
```

`aggregatorTransform.js` does not map `od.delivery_man_id` → `deliveryManId`. `hasRiderAssigned` is always `false`. This breaks the "Change Rider / Waiting for Rider / Reassign" button logic at `OrderCard.jsx:1139–1156`.

### GAP-R4 — Low: `riderInfo` Nested Object Is Dead Data

`aggregatorTransform.js:87–94` emits a `riderInfo` nested object with fields `id`, `name`, `phone`, `channel`, `returnOtp`, `bagReturnOtp`. No UI component reads `order.riderInfo` — confirmed by full-codebase grep. These fields are orphaned.

### GAP-R5 — Medium: Socket Rider-Assign Bypasses Aggregator Transform

`socketHandlers.js:623`:
```js
order = orderFromAPI.order(payload.orders[0]);  // POS orderTransform, not aggregatorTransform
```

`handleDeliveryAssignOrder` routes through `orderTransform.fromAPI.order()` which expects a `delivery_man` POS object — not `rider_info` (UrbanPiper shape). A live socket rider-assign event will overwrite an aggregator order with POS schema, losing all `rider_info` data. Even if GAP-R1–R3 are fixed on initial load, socket refresh will regress the display to "Awaiting Runner".

## 6. Files Affected

| File | Nature of Change Needed |
|---|---|
| `src/api/transforms/aggregatorTransform.js` | Add `rider:` key (maps to `rider.name`); add `riderStatus` derivation; add `deliveryManId` mapping |
