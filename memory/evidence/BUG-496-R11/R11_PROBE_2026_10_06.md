# R11 API PROBE — BUG-496: Does pmsCheckIn store gst_tax in folio?

**Date:** 2026-10-06
**Probe by:** INVESTIGATION agent
**Orders probed:** 1232976 (#000326, 80% discount, bp=0) · 1232973 (#000325, 89% discount, bp=0) · 1232970 (40% discount, bp=2665)

## QUESTION

Does the backend **store** `gst_tax` from the `pmsCheckIn` payload into the folio's `room_info`? If not, is E-496-5 (changing `gstBase` at check-in) a no-op?

---

## CONCLUSIONS

### C1 — E-496-5 is a NO-OP for folio

`gst_tax` sent in `pmsCheckIn` payload is NOT stored anywhere in `room_info`. The field is entirely absent. Changing `gstBase` at check-in (E-496-5) does NOT affect any folio-visible data.

### C2 — E-496-5 affects `balance_payment` send value, but backend ignores it

The `balance_payment` field in the `pmsCheckIn` FormData is computed as `orderAmount + gstTax - advance`. But the backend OVERRIDES this with `room_price - discount - advance`. No visible effect on folio state.

### C3 — LR GST fields NOT updated

LR `charge.sgst`/`charge.cgst` are set at reservation creation and NOT updated when a check-in discount is applied. They remain at full-price values. This is a known gap (P3 in INV-496 is about checkout GST, not LR GST).
