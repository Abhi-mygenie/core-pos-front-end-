# B0 VALIDATION PROBE — BUG-498/499: Does backend 422 when room_discount > 0 and bp=0?

## QUESTION

When `room_discount > 0` is sent to `order-bill-payment` for an order where `balancePayment = 0` (fully pre-paid via advance after check-in discount), does the backend reject with **HTTP 422** (validation error) or accept with **HTTP 200**?

**Payload (key fields):**

---

## B0 CONCLUSIONS

### C1 — Backend does NOT validate room_discount ≤ balance_payment

Both `room_discount=0` (absent) and `room_discount=100` for a `bp=0` unpaid order produce the **exact same** SQL error at the same column. The backend makes NO distinction based on room_discount value. There is NO 422 validation for room_discount > balance_payment.

### C2 — B0 probe PASSES

**The backend handles `room_discount > 0` when `balance_payment = 0` without any 422.** BUG-498/499 implementation is safe to proceed. The fix formula (`roomDiscountRs` based on `baseBalance`) will produce correct ₹ amounts and the backend will accept them.

### C3 — 500 error is probe-payload issue, NOT a backend gate

The `restaurant_discount_amount cannot be null` error is because the probe payload was missing a field that maps to this DB column (likely `coupon_discount_amount` or similar composite field that frontend normally sends). This does NOT indicate a room_discount validation gate.

### C4 — Alignment with handover_5 §4.4

Result confirms handover_5 §4.4 proof (order 1232889): `room_discount_apply_to = both` with positive `room_discount` on `bp=0` order → valid, no 422. Current probe is consistent.
