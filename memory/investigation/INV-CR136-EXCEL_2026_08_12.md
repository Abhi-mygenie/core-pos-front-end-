## 1. Summary

**Finding:** The backend endpoint `POST /api/v1/vendoremployee/top-food-variation-sales-report-download` **EXISTS and is LIVE**. It returns a pre-generated `.xlsx` file covering **all 3 data sets** — Food Sales, Variation Sales, and Addon Sales — in a single download. This is **strictly better UX** than the current CR-136 implementation which has two separate download buttons (one for Item Sales, one for Variation/Addon). However, the backend file has richer fields (Addon ID, Food ID, Variation Group, VAT, Service Charge) and fixed columns — while the FE Excel respects the column chooser and adds By-Category / By-Station breakdown tabs.

**Recommendation:** Migrate CR-136 to use the backend endpoint as PRIMARY download. Keep FE export as FALLBACK.

**Classification:** OWNER_DECISION (tradeoffs exist — see §5)
**FE fix needed:** YES — replace/supplement current FE Excel with backend endpoint call
**Planning skip eligible:** NO — touches `topFoodSalesService.js`, `ItemSalesLedgerMockup.jsx`, `VariationAddonMockup.jsx` (3 files, non-hotspot, but needs Gate 2-3 for scoping)

## 6. Concurrency Risk — IMPORTANT ⚠

The backend stores the file as a **fixed static path**:
```
/storage/top_food_variation_sales_report.xlsx
```

This means:
- If Restaurant A and Restaurant B both trigger the download at the same time, **Restaurant B's file will overwrite A's URL**.
- Restaurant A clicking the returned URL would get **Restaurant B's data**.
- This is a **data privacy concern** at scale, though low-risk on preprod.

**This must be flagged to the backend team as a BLOCKER before using this endpoint in production.**
The fix is simple: use a unique path per user/restaurant/request:
```
/storage/top_food_variation_sales_{rid}_{timestamp}.xlsx
```

## 7. Recommendations

### Option A — Replace FE Excel with Backend Endpoint (RECOMMENDED, with caveat)
- One "Download Excel" button on BOTH screens → calls backend endpoint → opens `download_url`
- Replaces both current FE Excel downloads with a single richer file
- **Requires backend concurrency fix first** (static filename → unique per request)
- FE change: add `downloadTopFoodVariationReport(from, to)` to `topFoodSalesService.js` (same pattern as `exportOrderReportBetaExcel`)

### Option B — Hybrid (Backend Excel + Keep FE as fallback)
- Primary button → backend endpoint
- Secondary option → FE Excel (for column-chooser / By-Category-Station users)
- More complex UX

### Option C — Keep FE Excel, ignore backend endpoint
- Maintains column chooser, By Category, By Station tabs
- But loses Addon ID, Food ID, Variation Group, VAT, Service Charge, single-file convenience
- No backend dependency

**Owner decision needed on:**
- **OD-1:** Accept backend concurrency risk on preprod now, or wait for backend fix first?
- **OD-2:** Are By-Category and By-Station tab breakdowns in the Excel needed by users? (If yes → hybrid or keep FE)
- **OD-3:** Is column chooser compliance in the export required? (If yes → hybrid or keep FE)

## 8. Recommended FE Implementation (Option A — if owner approves)

**New function in `topFoodSalesService.js`:**
```javascript
// CR-136 Amendment — backend Excel endpoint
export const downloadTopFoodVariationReport = async (fromDate, toDate) => {
  const response = await api.post(
    '/api/v1/vendoremployee/top-food-variation-sales-report-download',
    { from: fromDate, to: toDate }
  );
  const url = response.data?.download_url;
  if (url) {
    window.open(url, '_blank');
    return { success: true, url };
  }
  throw new Error('No download_url in response');
};
```

**Changes in `ItemSalesLedgerMockup.jsx`:**
- Replace `exportReportAsExcel(...)` call with `downloadTopFoodVariationReport(appliedFrom, appliedTo)`
- Remove the FE Excel button from `VariationAddonMockup.jsx` (backend file covers it too)
- OR keep FE Excel as a secondary option

**Scope:** SMALL — 2-3 non-hotspot files, ~20 lines total. No R5/R6 risk.
