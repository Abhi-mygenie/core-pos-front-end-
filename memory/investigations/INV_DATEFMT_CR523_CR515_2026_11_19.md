## 2. I-1 — Date format inconsistency (Cancellation Report)

**File:** `pages/reports-module/CancellationsMockup.jsx`

| Line | Render | Output style |
|---|---|---|
| L736, L954 | `{r.orderDate} {r.orderTime}` (raw API `cancel_date` + `cancel_time`) | `2026-10-01 19:31` |
| L980 | `new Date(r.punchTime).toLocaleString('en-IN', { hour:'2-digit', minute:'2-digit', hour12:true, day:'2-digit', month:'short' })` | `01 Oct, 06:51 pm` |

Two different date formats appear in the **same row** (matches the owner's green-highlighted screenshot columns).

**Recommendation:** Standardize both columns (ideally a shared `formatDateTime()` util used across reports) to one format. Display-only, LOW risk. Planning-skip eligible (owner approve).

## 3. I-2 — CR-523 Customer Name not capturing

**FE SAVE PATH — VERIFIED CORRECT (hypothesis "early-return" ELIMINATED):**
```
CartPanel name input (L1135 data-testid="quick-customer-name")
  → onBlur → handleFieldBlur (L1048) → onCustomerChange(merged {name, phone,...})
  → OrderEntry L2966: setCustomer + saveCustomerToServer(customerData)
  → saveCustomerToServer (L1109): orderId = effectiveTable?.orderId
     effectiveTable = { ...table, orderId: placedOrderId || table?.orderId }  (L281)
     → for a PLACED order placedOrderId is set → guard PASSES → POST user-check-create { f_name, phone, order_id }
```
So for a placed order the name IS posted. The early-return guard does NOT block it.

**REHYDRATION PATH — where the blank shows:**
```
Reopen order → OrderEntry L433/L479: resolvedName = orderData.customerName || roomInfo.guestName || ''
  → orderData.customerName  ← orderTransform L220 `customerName: customer`
     where customer = api.user_name || (user.f_name + user.l_name)   (L179-181)
  → CartPanel syncs field from customer.name (L903, L931-935)
```
Screenshot: phone `9035133228` persists but **name is blank** on an 888-min-old order. Since phone survives the round-trip but the first name does not, the order read-back (`api.user_name` / `api.user.f_name`) is empty — i.e. the name saved via `user-check-create` is **not reflected on the order record** returned by `SINGLE_ORDER`.

**Classification:** BACKEND linkage / read-back gap (FE correct). **Needs live read-only probe:** open an order that had a customer linked via the quick-customer field and inspect the `SINGLE_ORDER` response for `user_name` / `user.f_name`.
- If blank → backend `user-check-create` is not persisting `f_name` to the order (or `SINGLE_ORDER` doesn't surface it) → backend brief.
- If populated → FE mapping gap in `orderTransform` (unlikely; mapping present at L179-181/L220).

**Secondary FE note (MEDIUM):** `handleFieldBlur` (L1062-1088) runs an async CRM `lookupCustomer`; if the phone matches an existing CRM record it re-emits `onCustomerChange` with `enriched.name || merged.name`. A blank CRM name keeps the typed name (safe), but a *stale* CRM name would overwrite the typed one. Worth confirming during the probe.

## 4. I-3 — CR-515 Bill reprint without print rights

**I-3a — Order Report (CONFIRMED CODE_ERROR, HIGH):**
```
pages/reports-module/OrderReportBetaPage.jsx
  L779:  {row.f_order_status === 6 && (            ← ONLY status gate, NO permission
  L781:    <button onClick={() => handleReprint(row)} data-testid=`reprint-btn-${order_id}`>Reprint</button>
  L372 handleReprint → printOrder(order_id, 'bill', ...)   ← prints the BILL
```
Sibling actions on the same page ARE gated: `update_payment` (L753), `order_unpaid` (L763), `clear_payment` (L814). Only **Reprint** is missing `hasPermission('print_icon')`.
**Fix:** add `hasPermission('print_icon') &&` to the L779 condition. 1 file, 1 line, LOW risk, planning-skip eligible (owner approve).

**I-3b — Dashboard (NEEDS LIVE PROBE, MEDIUM):**
In code the dashboard bill/print actions ARE already gated by `print_icon`:
```
OrderEntry L361: const canPrintBill = hasPermission('print_icon');
OrderEntry L2878: {canPrintBill && hasPlacedItems && (orderId) && <PrintBillButton/>}   ← Print Bill (bill)
CartPanel L1315 / L1379: {canPrintBill && ...}  <RePrintOnlyButton/>                     ← "Re-Print" = KOT reprint (printOrder 'kot'), not bill
```
So if the screenshot role sees these buttons, either that role actually HAS `print_icon`, or `hasPermission('print_icon')` is returning true unexpectedly for it. Cannot confirm without the **specific limited role's** credentials (owner@cafe103 has all permissions, so cannot reproduce). Probe: log in as the no-print role → inspect the permissions array for `print_icon`.

**Secondary gap (owner decision):** the Collect-Bill/payment flow prints a bill but is gated by `clear_payment` (not `print_icon`). A user with collect rights but no print rights can still trigger a bill print during collection. Decide whether that path should additionally require `print_icon`.
