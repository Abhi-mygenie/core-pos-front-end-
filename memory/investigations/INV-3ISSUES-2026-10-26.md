## ISSUE 1 — Double Discount in Role-Based Discount

**ID:** BUG-619 (register)  
**Confidence:** HIGH  
**Classification:** CODE_ERROR (introduced by BUG-614 QA fix)  
**Owner:** owner@mantri.com · Order 001405 (API probe returned empty — order likely settled)  

### Root Cause

After the BUG-614 fix (which made preset discount Apply work), a double-counting regression was introduced. Exact sequence:

**Step A — User selects preset and clicks Apply:**
```
User selects "Family — 50%" from dropdown:
  → setSelectedDiscountType({ discountPercent: 50, name: 'Family' })
  → setDiscountType(null)
  → setDiscountValue('')

User clicks Apply → handleApplyDiscount (preset path):
  → applyOrderDiscount({ discountAmount: 50, discountType: 'percent', discountNote: 'Family' })
  → setIsDiscountApplied(true)
  → selectedDiscountType still = { discountPercent: 50 }
```

**Step B — Socket re-seeds state (BUG-595 reactive useEffect fires):**
```
Backend saves discount_amount: 50, discount_type: 'percent'
Socket fires → liveOrder.orderDiscountJson = { discount: 50, discountType: 'percent', discountNote: 'Family' }

useEffect at CPP L369-376:
  setDiscountType('percent')    ← NOW discountType = 'percent'
  setDiscountValue('50')        ← NOW discountValue = '50'
  setIsDiscountApplied(true)
  ⚠️  setSelectedDiscountType(null) is NEVER called
      → selectedDiscountType STILL = { discountPercent: 50 }
```

**Step C — Double count in render:**
```js
// CPP L681-687 (both non-zero simultaneously):
const presetDiscount = selectedDiscountType
  ? Math.round(discountableTotal * 50) / 100   // = 50% of total ← from selectedDiscountType
  : 0;

const manualDiscount = discountType === 'percent'   // true: 'percent' === 'percent'
  ? Math.round(discountableTotal * parseFloat('50')) / 100  // = 50% of total ← from discountValue='50'
  : ...;

const totalDiscount = manualDiscount + presetDiscount = 100% of order total  ← DOUBLE DISCOUNT
```

**Also in payment payload (CPP L1197-1198):**
```js
discounts: {
  manual: manualDiscount,   // 50% ← wrong, should be 0
  preset: presetDiscount,   // 50% ← correct
  total: totalDiscount,     // 100% ← wrong
}
// → collectBillExisting sends self_discount = manual + preset = 100%
```

### Evidence
- Code trace: CPP L339-417 (state declarations → handleApplyDiscount → render L681-709)
- Break point: useEffect L369-376 does NOT call `setSelectedDiscountType(null)`
- Confirmed: `presetDiscount` and `manualDiscount` are independently computed from different state (not mutual exclusive)

### Recommended Fix (1 line, CPP R5 hotspot — owner approval needed)
```js
// CPP L369-376 — add 1 line:
useEffect(() => {
  if (!initialDiscount) return;
  setDiscountType(initialDiscount.discountType);
  setDiscountValue(String(initialDiscount.discount));
  setDiscountFor(initialDiscount.discountNote || '');
  setIsDiscountApplied(true);
  setSelectedDiscountType(null); // ← ADD THIS: clear preset so socket re-seed only populates manualDiscount
}, [initialDiscount?.discount, initialDiscount?.discountType]);
```

After fix: `selectedDiscountType=null → presetDiscount=0`. `discountType='percent', discountValue='50' → manualDiscount=50%`. `totalDiscount=50%` ✅

**Risk:** LOW — change is additive null-set, preserves all non-preset paths

## ISSUE 2 — List View Shows Old Order Ordering After Socket Update

**ID:** BUG-620 (register)  
**Confidence:** HIGH  
**Classification:** CODE_ERROR (list view missing sort, card view has sort)  

### Root Cause

The dashboard has two views. **Card view** (channel/status) calls `sortByActiveFirst()` on every render. **List view** renders `allTablesList` in RAW INSERTION ORDER — no sort is ever applied.

**Card view (L1916):**
```js
{sortByActiveFirst(
  filteredGridItems.filter(...),
  TABLE_STATUS_PRIORITY       // ← re-sorts on every render by status priority
).map((item) => <TableCard ... />)}
```

**List view (L1966):**
```js
{allTablesList
  .filter(t => !["available", "reserved"].includes(t.status))
  .filter(t => matchingTableIds === null || matchingTableIds.has(t.id))
  .map((table) => { ... })}  // ← NO sortByActiveFirst → uses API call order
```

**What happens on socket update:**
1. Socket fires `updateOrder` → `orders` array changes (new reference)
2. `tables` useMemo (L545) depends on `getOrdersByTableId` from OrderContext → recalculates → `allTablesList` reflects updated `tableStatus`, `fOrderStatus`, etc.
3. **Card view**: calls `sortByActiveFirst` → orders re-sorted by new status (e.g., billReady moves to top)
4. **List view**: renders `allTablesList` in original insertion order → order stays at its original position even though status changed
5. After full API refresh (`setOrders(fresh)`): entire `orders` array is replaced → `allTablesList` rebuilt from scratch → correct order in both views

### Evidence
- `allTablesList` useMemo L679: `[tables, flatTables, hasAreas]` deps — no `orders` directly, but `tables` useMemo at L545 calls `getOrdersByTableId()` which reads from `orders`
- `adaptTable` at L569-591: table entries' `status` = `order.tableStatus`, `fOrderStatus` = `order.fOrderStatus` — these ARE updated on socket
- BUT the POSITION of entries in `allTablesList` is fixed by `apiTables` iteration order — socket update changes STATUS but not POSITION
- Card view re-sorts on every render → position reflects new status
- List view uses fixed position → status changes are invisible in ordering

### Recommended Fix (DashboardPage.jsx — non-hotspot)
Apply `sortByActiveFirst` to the list view render, same as card view:
```jsx
{/* List view L1966 — add sort: */}
{activeChannels.includes("dineIn") && sortByActiveFirst(
  allTablesList.filter(t => !["available", "reserved"].includes(t.status))
               .filter(t => matchingTableIds === null || matchingTableIds.has(t.id)),
  TABLE_STATUS_PRIORITY
).map((table) => { ... })}
```

Apply same sort to delivery and takeaway sections in the list view for consistency.

**Risk:** LOW — uses same `sortByActiveFirst` already used in card view; no logic change

## ISSUE 3 — PWA Update Button Not Showing

**ID:** BUG-621 (register)  
**Confidence:** HIGH  
**Classification:** CODE_ERROR (architectural conflict between skipWaiting + waiting detection)  

### Background
BUG-597 implemented: `skipWaiting()` in SW install + `clients.claim()` in activate + `controllerchange → reload` + `reg.waiting` detection for banner.

### Root Cause

There is a fundamental conflict between `skipWaiting()` and the `reg.waiting` detection:

**SW lifecycle WITH `skipWaiting()` (firebase-messaging-sw.js L81-82):**
```
1. New SW version downloads
2. install fires → self.skipWaiting() ← SW immediately skips waiting
3. SW activates (never enters 'waiting' state)
4. activate fires → self.clients.claim()
5. controllerchange fires in app → window.location.reload() (immediate, no banner)
```

**Why `reg.waiting` is always null:**
```js
// NotificationContext.jsx L237-241:
navigator.serviceWorker.ready.then((reg) => {
  if (reg.waiting) setSwUpdatePending(true);        // ← NEVER true (SW skip-waited past this)
  reg.addEventListener('updatefound', () => {
    if (reg.waiting) setSwUpdatePending(true);      // ← race condition: by the time this fires,
                                                    //   installing SW has already skip-waited → waiting = null
  });
});
```

**Result:**
- Banner (`swUpdatePending=true`) is NEVER shown
- `controllerchange → window.location.reload()` fires immediately — no user warning in browser
- In PWA: app backgrounded → SW updates → `skipWaiting()` → `clients.claim()` → `controllerchange` fires but React app may not be mounted → `window.location.reload()` may not execute → user reopens PWA still on old version

**Why it's worse in PWA specifically:**
- PWA tabs can be "frozen" (suspended) by OS when backgrounded
- JS event listeners (including `controllerchange`) don't fire while frozen
- New SW activates silently in background
- User opens PWA: new SW is already in control, no `controllerchange` fires, `reg.waiting` is null → NO banner, NO reload
- User sees old cached assets served by new SW → possible broken state

### Recommended Fix (No code edit per owner — investigation only)

Two options:

**Option A — Remove skipWaiting from SW, add message listener (correct PWA pattern):**
```js
// firebase-messaging-sw.js — REMOVE:
// self.addEventListener('install', () => { self.skipWaiting(); });

// ADD message listener:
self.addEventListener('message', (event) => {
  if (event.data?.action === 'skipWaiting') self.skipWaiting();
});
```

```js
// NotificationContext.jsx — when reg.waiting detected:
// Call reg.waiting.postMessage({ action: 'skipWaiting' }) on user click
// Banner shows → "Reload now" → postMessage → skipWaiting → controllerchange → reload
```

**Option B — Keep skipWaiting, but detect via `navigator.serviceWorker.controller` change on app open:**
```js
// On app open in PWA, compare SW scriptURL with cached known version
// If changed → show banner → user can reload
```

Option A is the correct PWA pattern. The banner will then show reliably in both browser and PWA because the SW waits until user approval.

**Files involved:** `public/firebase-messaging-sw.js` + `src/contexts/NotificationContext.jsx` + `src/App.js` (SwUpdateBanner)
