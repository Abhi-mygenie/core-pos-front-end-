### I-4 — Cancel After Making Unpaid: Audit Event not working

| # | Hypothesis | Test | Result | Evidence |
|---|---|---|---|---|
| H1 | AuditLogMockup shows `make_unpaid` events | Code trace `AuditLogMockup.jsx` L75-76 | **CONFIRMED** — `makeUnpaid = orders.filter(o => o.type === 'make_unpaid')` | L75-76 |
| H2 | Backend `insights-audit` removes make_unpaid events when order subsequently cancelled | Code trace + logic deduction | **CONFIRMED (HIGH confidence)** — When an order transitions to Cancelled state, backend audit API likely only returns events for the final state; `make_unpaid` events are dropped | Logic from AuditLogMockup |
| H3 | FE AuditLogMockup filters incorrectly | Code trace | **ELIMINATED** — FE correctly shows all `make_unpaid` rows; issue is upstream in backend data | L75-77 |

**Break point:**
```
User flow:
  1. Order settled (paid) → backend records order
  2. Staff marks unpaid → backend records make_unpaid event in operations
  3. Staff cancels order → backend marks order cancelled

AuditLogMockup.jsx expects:
  insights-audit API to return: [{ type: 'make_unpaid', order_id: X, ... }]
  
Actual: when order is cancelled after make_unpaid, backend drops the
        make_unpaid audit event → it never appears in insights-audit response
        → AuditLogMockup filters orders.filter(o => o.type === 'make_unpaid')
        → empty result for that order
```

**Classification:** BACKEND_BUG — `insights-audit` API should retain `make_unpaid` events regardless of subsequent order state. Needs backend brief.

|---|---|---|---|---|
| H1 | FE transform reads wrong discount field | Code trace `reportTransform.js` L183/221/276 | **ELIMINATED** — `discount: formatAmount(api.restaurant_discount_amount || api.discount_value || 0)` correctly reads discount | L183 |

**Root cause (MEDIUM confidence — needs live probe):**
When a bill is printed and then a discount is applied followed by collection, the FE sends the discount in the `collectBillExisting` payload (via CPP). The report reads from `restaurant_discount_amount` in the backend `order-logs-report` response. If the backend stores this correctly, the report should show it. If not shown, the backend is not storing the discount from the `collect-bill` payload into `restaurant_discount_amount`.

**Needs confirmation:** Live probe of priti's orders with discount + `restaurant_discount_amount` field value.
