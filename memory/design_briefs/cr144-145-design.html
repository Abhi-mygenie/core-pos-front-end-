OPEN QUESTIONS — 5 DECISIONS NEEDED

OQ-1 · Expand Pattern

How to edit addons per row?
RECOMMENDED

Option A — Sub-row inline

Clicking the chip opens a sub-row directly below in the table. Checkbox list of all addons; pre-checked = currently assigned. Apply button saves.

✔ Consistent with table layout · No context loss · Simpler to implement · One row at a time

✗ Scrolling needed for 97+ rows; sub-row adds height

ALTERNATE

Option B — Side drawer

Clicking the chip slides open a right-side drawer (like ProductForm) showing the full addon list for that food.

✔ More space for future features

✗ Hides the table · Breaks BulkEditor's "spreadsheet feel" · Higher implementation complexity

OQ-2 · Row Dimming

When expanded, should other rows dim?
RECOMMENDED

Option A — No dimming

Other rows remain fully visible. Only the expanded sub-row and its parent row are highlighted (green tint). User can close panel and open a different row freely.

✔ Simpler · Less intrusive · User can still scan other rows

✗ Slightly busy if many rows

ALTERNATE

Option B — Dim other rows

All other rows are dimmed (opacity 0.4) when one row is expanded, like a modal overlay effect.

✔ Clear focus state

✗ More CSS complexity · Can't compare addons across rows

OQ-3 · Variation Column Depth

Read-only summary or allow edits?
RECOMMENDED

Option A — Read-only summary

Variation column shows group count chip. Expanding shows group names + values (as shown in mockup above). No editing. Footer link: "Full variation edit in Product Form".

✔ Low risk · No new API writes needed · Safe for P2 priority item · Scope-limited

✗ Users can't edit variations in bulk (but full edit is available via ProductForm)

ALTERNATE

Option B — Allow option-value edits

Let users add/remove option values within existing variation groups. POST /product/manage-variation per change.

✔ More powerful

✗ Significant risk · Complex dirty tracking · Multiple API write paths · Should be a separate CR

OQ-4 · Addon List Fetch

When to fetch the restaurant addon pool?
RECOMMENDED

Option A — Fetch once on BulkEditor mount

BulkEditor receives addons prop from MenuManagementPanel (already fetched on panel open). No new fetch needed — BulkEditor already receives this prop today.

✔ Zero new API calls · Addons already in memory from MenuManagementPanel · Restaurants typically have <50 addons

✗ Stale if user adds a new addon mid-session (but refresh button handles this)

ALTERNATE

Option B — Fetch lazily per-row on first expand

Fetch addon list only when user first expands a row. Cache result for subsequent expansions.

✔ Always fresh

✗ Unnecessary complexity; 97-row BulkEditor doesn't need per-row fetches for a <50 item addon list

OQ-5 · Dirty State for Arrays

How to detect addon assignment changes?
RECOMMENDED

Option A — Sorted JSON.stringify comparison

On expand, snapshot the food's current addon_ids[]. On Apply, compare sorted stringified arrays: JSON.stringify([...new].sort()) !== JSON.stringify([...original].sort()). If different, mark row dirty + include addon_ids in buildPayload().

✔ Accurate · Simple to reason about · No dependency on order of selection

✗ Slightly heavier than integer comparison (negligible for <50 addons)

ALTERNATE

Option B — Shallow length + Set check

Compare lengths first, then use Set symmetric difference: new.some(id => !origSet.has(id)) || orig.some(id => !newSet.has(id)).

✔ Slightly faster

✗ More code to maintain · No real performance gain for <50 addons
