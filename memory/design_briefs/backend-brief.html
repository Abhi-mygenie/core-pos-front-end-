Backend Brief — FE Aggregation Endpoints
MyGenie POS · Insights Module · 1-Year Range Expansion
2026-07-10 From: Frontend Investigation Agent CONTRACT_MISMATCH / NEW_ENDPOINT_REQUEST P1 — Blocks 1-year range for 5 screens

Context

Five Insights reports currently fetch raw order-logs-report data and aggregate entirely in the browser. This works for small date ranges but becomes unsafe for 1-year ranges on high-volume restaurants (potential 100 MB+ payloads, browser freezes).

  • Each report needs a dedicated backend aggregation endpoint.
  • All new endpoints must follow the same contract as existing insights-* endpoints.
  • Method: POST  |  Auth: Bearer JWT  |  Body: { "from_date": "YYYY-MM-DD", "to_date": "YYYY-MM-DD" }
  • Envelope: { "success": true, "data": { ... } }

insights-tab-settlements
Order Ledger — Tab (Credit) settlement data · P1 — Simplest, do first
POST/api/v2/vendoremployee/report/insights-tab-settlements
Why this exists

The Order Ledger currently calls daily-sales-revenue-report once per day for N days to get tab settlement breakdown. For a 60-day range = 60 API calls. This is the only bottleneck preventing Order Ledger from supporting 1-year ranges. The order-logs-report part already handles 1-year in a single call.

What the FE currently extracts per day
// From: daily-sales-revenue-report (called once per calendar day)
const tp = data.paid_revenue_method?.tab_payment || {};
cash = tp['Credit Cash']
card = tp['Credit Card']
upi  = tp['Credit UPI']
Required Response Shape
{
  "data": {
    "tab_settlements": [
      {
        "date":         "2026-07-01",       // YYYY-MM-DD
        "date_display": "01/07/2026",       // DD/MM/YYYY for display
        "cash":         1200.0,
        "card":         800.0,
        "upi":          500.0,
        "total":        2500.0
      }
      // ... one row per calendar day in range
    ],
    "summary": {
      "total_cash": 45000,
      "total_card": 28000,
      "total_upi":  19000,
      "total":      92000
    }
  }
}
Important Notes
  • Return one row per calendar day in the requested range, even if total = 0 — FE needs a full date spine for chart rendering.
  • date_display format: DD/MM/YYYY
  • This is the simplest of the 5 endpoints — just a range wrapper over the existing daily-sales-revenue-report logic.

BUG-183 — Credit Tab: Customer Name & Phone Missing
Daily Report → "Added to Credit" tab  ·  P1 · MEDIUM  ·  BACKEND-ONLY FIX
POST/api/v2/vendoremployee/report/order-logs-report
Problem

In Daily Report → "Added to Credit" tab, every row shows Guest for customer name and — for phone — regardless of whether the customer was identified at order time.

Impact: Staff cannot identify who owes the credit. The Credit tab is operationally useless without this data.

Root Cause

The FE wiring is 100% correct — the bug is entirely on the backend side:

// reportTransform.js:258-266 — FE already maps correctly:
customer: api.user_name || 'Guest',       // ← defaults to 'Guest' when null
phone:    api.cust_mobile || api.user_phone || api.phone,

// BUT for TAB/credit orders in the API response:
user_name:   null,    // ← backend does not populate this
cust_mobile: null,    // ← backend does not populate this

For non-TAB orders (Cash, Card, UPI), user_name and cust_mobile are populated correctly. Only TAB/credit-settled orders are missing these fields.

Fix Required
  • Populate user_name and cust_mobile for TAB-settled order rows in order-logs-report, sourced from the customer record linked to the order.
  • No change to response envelope or key names — FE reads the same fields.
  • No FE changes needed after backend delivers.
FE Status

Zero FE changes needed. reportTransform.js, OrderTable.jsx — already correct. The customerPhone column is specifically rendered for the Credit tab (OrderTable.jsx:196-200).
