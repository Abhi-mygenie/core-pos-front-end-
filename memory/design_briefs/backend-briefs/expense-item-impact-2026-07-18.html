Expense Item Deletion Impact Endpoint

Required to power the cascade-warning dialog shown before an expense item is deleted — prevents silent destruction of financial transaction history (BUG-201).

P1 · HIGH
Filed: 2026-07-18
From: Frontend (Planning Gate 2)
Sprint: pos_5_0
Data-loss risk

Why this matters

Deleting an expense item currently triggers cascade deletion of all related expense transactions on the backend (DELETE /expense/expenses/{id}). The FE only shows a generic window.confirm("Delete?") — the operator has no idea historical financial records will be destroyed. To ship a safe destructive-confirmation dialog, FE needs to know upfront how many transactions and what ₹ value will disappear.

Consuming widget

Cascade-Warning Dialog
Fires when user clicks delete on an item in ExpenseSetupPanel.jsx — before the actual DELETE call.
⚠ Delete "Electricity Bill"?

This item has 12 expense transactions totalling ₹18,500
across Jun 01, 2026 – Jul 15, 2026.

Deleting will permanently remove the item AND all related expense records.

  [Cancel]     [Delete Item + 12 Transactions]

Proposed endpoint

MethodGET
Path/api/v2/vendoremployee/expense/item/{id}/impact
AuthBearer token · same as existing expense endpoints
URL Paramid — expense item PK (from expenses.id)
Required

Response shape (minimum · P1)

{
  "success": true,
  "data": {
    "item_id":           12345,
    "item_name":         "Electricity Bill",
    "transaction_count": 12,            // how many expense_transactions rows will cascade-delete
    "total_amount":      18500.00,      // SUM(amount) across those rows, in ₹
    "date_range": {
      "first": "2026-06-01",             // earliest transaction date · null if 0 rows
      "last":  "2026-07-15"              // latest · null if 0 rows
    }
  }
}

Empty case: return transaction_count: 0, total_amount: 0, date_range: { first: null, last: null }. Do not return 404 — a "clean item with no transactions" is a valid, common case that shows a lighter confirm dialog.

Nice-to-have

Optional enrichments (P2)

  • transactions_by_month — array of { month, count, total } for a mini-bar in the dialog.
  • last_transaction_by — { user_id, user_name } of who logged the most recent one.
  • category_id / category_name — for context (dialog can show "in category: Utilities").

Business rules

#RuleDecision
1Which transactions are counted?All rows in expense_transactions where item_id = {id} — regardless of date, payment method, or user. Same rows that would cascade-delete on DELETE /expense/expenses/{id}.
2Restaurant scopingOnly transactions belonging to the authenticated restaurant. Master outlets do not see children's counts here — impact is local.
3Aggregate totals sync (§B14)After the actual DELETE /expense/expenses/{id} call, any aggregated totals endpoint (expense report, dashboard KPIs, category counts) MUST auto-recompute from live data — no denormalised caches. FE will not fire a manual re-cache signal.
4Non-existent itemReturn 404 with { code: "ITEM_NOT_FOUND" }.
5PerformanceShould respond in < 200 ms even for high-volume items — a single indexed COUNT(*) + SUM(amount) is enough. No pagination needed.

Acceptance criteria (FE will test)

  1. New item with 0 transactions → transaction_count: 0, total_amount: 0, date_range: {first:null,last:null}. HTTP 200.
  2. Item with N transactions → transaction_count: N, total_amount equals SUM shown on Expense Report filtered by that item.
  3. After DELETE /expense/expenses/{id}, the same GET returns 404.
  4. After delete, the aggregate totals endpoint (Expense Report for the same range) shows the expected reduction — proves Business Rule 3.
  5. Response latency < 200 ms for any item, regardless of history size.
  6. Cross-restaurant call returns 403.
