Food Court Order Report Endpoint

New endpoint required to power the Food Court Report with per-order rows pre-filtered and pre-aggregated by station on the backend — eliminating FE-side aggregation, batching, and large payload transfers.

P1 · MEDIUM NEW ENDPOINT
Filed: 2026-08-12
From: Frontend · Investigation Gate
Sprint: pos_5_1

The Problem — Why This Is Needed

The Food Court report currently works by calling order-logs-report (returns ALL orders for the restaurant), then filtering and aggregating per-station entirely on the frontend. For the Shimla Food Court this means:

Current — 1 month
817 full order wrappers downloaded · FE loops every item · 3 parallel calls for >30d · batch progress bar UI
With this endpoint — any range
1 API call · backend filters by station · only 254 order rows returned · FE renders directly · no batching
Existing alt endpoint
top-food-sales-report gives aggregated items — but no order IDs. Cannot show order-level view.

Live evidence from preprod.mygenie.online (Shimla Food Court, July 2026): 817 total orders · 4 stations · GUPTAJEE had 254 orders (₹96,612) · MSB 137 orders · ZORKO 332 · CREAMBELLPARLOUR 355. With a station filter, only 31% of the payload is needed (GUPTAJEE case).

Existing endpoints — what they do and why neither is sufficient

EndpointReturnsGap
POST /api/v2/vendoremployee/report/order-logs-report Raw per-order wrappers with all items for all stations FE must filter items by station, compute proportional discount, sum GST per station. Heavy FE computation. Full payload always transferred.
POST /api/v1/vendoremployee/top-food%20sales-report food_item × station aggregated totals (qty, revenue, GST, discount) No order IDs, no order date/time, no payment method. Cannot show per-order rows. Audit view impossible.
POST /api/v1/vendoremployee/food-court-order-report NEW Per-order rows pre-filtered by station with station-scoped financial breakdown — This is what we need

Business rules

#RuleDecision
1 Station filtering Include only items where order_details_table.station === requested station. If an order has no items for the station, exclude it from orders[] entirely.
2 Proportional discount Order-level discount distributed proportionally by station's share of total order item price.
station_discount = order_discount × (station_item_total / order_item_total)
This is what the FE currently computes in foodCourtService.js:toStationRow().
3 Financial scope item_total, gst, vat reflect only items belonging to the requested station. Order-level charges (delivery, tip, round-off, service charge) are excluded — they are not attributable to a single station.
4 item_total calculation item_total = Σ(item.price + item.variation_price + item.addon_price) for non-cancelled items (food_status ≠ 3). Matches top-food-sales-report calculation.
5 NULL / unassigned station items Items with no station assignment (station IS NULL or '') → bucket under station = 'UNASSIGNED'. Include in stations[] list if any exist for this restaurant.
6 Order status filter Exclude fully cancelled orders (f_order_status = 3). Apply same filter logic as sort_by=collect_bill on order-logs-report.
7 Business-day boundaries Apply restaurant timezone-aware business day. A query for from: 2026-08-03 covers 2026-08-03 06:00:00 → 2026-08-04 03:00:00 (same as top-food-sales-report behaviour confirmed via probe).
8 Empty results Always return { "orders": [], "stations": [...], "total_orders": 0 }. Never return null or 404 for a valid auth + date range with no matching data.

Acceptance criteria (FE will verify)

  1. Calling with no station param returns { orders: [], stations: ["CREAMBELLPARLOUR","GUPTAJEE","MSB","ZORKO"], total_orders: 0 } — station list always populated.
  2. Filter station=GUPTAJEE for July 2026 returns 254 orders (verifiable against order-logs-report FE count).
  3. SUM(orders[].total) for GUPTAJEE ≈ ₹96,612.60 — must reconcile with top-food-sales-report GUPTAJEE station total.
  4. An order whose items span multiple stations (e.g. GUPTAJEE + MSB) appears under both stations when queried separately, with correct per-station financial split.
  5. Fully cancelled orders (f_order_status = 3) do not appear in results.
  6. Response for a 1-year date range returns in < 3 seconds — key performance requirement.
  7. Empty date range / no matching orders returns { orders: [], stations: [...], total_orders: 0 } with HTTP 200.
  8. All numeric fields are numbers (not strings). Contrast with top-food-sales-report where all row fields are strings — please use numbers here for direct FE rendering.
