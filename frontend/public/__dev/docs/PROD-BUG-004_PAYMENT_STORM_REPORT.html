Payment API Storm — paid-prepaid-order

Incident: 2026 · 21:18–21:21 IST  |  Report v2 (production-accurate, 2026-07-20)  |  Investigation: frontend code trace (full POS codebase) + backend agent server evidence  |  Related: PROD-BUG-001 · CR-077 · INV-SOCKET-001

TL;DR

The storm was generated by the POS Auto-Settle feature — a retry loop in DashboardPage.jsx:1418-1459 that re-POSTs paid-prepaid-order every ~10 seconds per stuck order, with no backoff, no max attempts, no batching, and no terminal state on success. Formula: (large backlog of unsettled status-5 prepaid orders) × (fire-all-at-once burst on dashboard open ~21:18) × (blind 10s retry until the order leaves the local list). The burst itself slowed the backend (lock contention → "request skipped" logs → slow responses → 499 client cancels), which delayed the clear signal, which caused more retries — self-worsening. Note (v2 correction): production does NOT have socket rooms; the room-rollout is irrelevant to this incident. Socket delivery flakiness at peak (legacy global-broadcast flood, INV-SOCKET-001) is only a contributing factor to the delayed clear signal.

2 · Root Cause — the Auto-Settle retry loop

Feature marker PROD-BUG-001 ("Auto Settle", toggle stored in localStorage mygenie_auto_settle_enabled, Status Config page). Actual code behavior:

// DashboardPage.jsx:1424 — effect runs on EVERY `orders` array change (socket events, polls, re-renders)
useEffect(() => {
  if (!autoSettleOn) return;
  // every prepaid order at fOrderStatus=5, not currently in-flight:
  candidates = orders.filter(o => o.fOrderStatus === 5 && o.paymentType === 'prepaid'
                                 && o.paymentMethod !== 'paylater' && !inFlight.has(o.orderId));
  candidates.forEach(o => {                       // ← ALL fired AT ONCE, no batching
    inFlight.add(o.orderId);
    completePrepaidOrder(o.orderId, ...)          // POST /api/v2/vendoremployee/order/paid-prepaid-order
      .finally(() =>
        setTimeout(() => inFlight.delete(o.orderId), 10000));
        // ← guard removed after 10s REGARDLESS of success or failure.
        // code comment: "allow retry if socket didn't clear"
  });
}, [orders, ...]);

3 · Why orders were "stuck" — backlog + slow clear signal (v2, production-accurate)

An order leaves the local orders list only via two paths:

A
Socket event — backend emits update-order (f_order_status=6 / 'paid') on settle; socketHandlers.js:290-320 drops terminal orders. Production still runs global broadcast (no rooms), so this path works — but it is least reliable exactly at peak: the legacy fleet-wide broadcast flood (INV-SOCKET-001) causes disconnects/missed events at busy hours, delaying removal.
B
60s poll / rehydration — mergeRunningOrders (OrderContext.jsx:48) replaces the list with fresh running orders. Clears the order only if the backend actually settled it. Lock-skipped / still-processing settles return at status 5 → loop refuels for another cycle.

The self-worsening cycle: ~200-order burst → backend lock contention ("Order payment request skipped because another request is processing" for many order IDs) → slow responses → client timeouts/cancels (499) → FE never registers success → 10s tick re-fires → more load. The per-minute decay is a textbook backlog-drain curve:

⚠ Check the IP attribution

172.31.39.21 is an AWS VPC private address — likely a load balancer / proxy node, not one client. The 2,789 requests may be many POS devices behind one LB hop. Attribute via X-Forwarded-For, the auth token, or the order_ids in request bodies — those identify the exact restaurant(s) and whether their devices run the old (no-join) build.

6 · Pattern Warning

This is the second "retry until socket clears" pattern to cause a production incident (first: socket GET-back herd, finding F2 of INV-SOCKET-001). Until the join-enabled frontend is universally deployed, every socket-dependent cleanup loop in the app degrades into its retry fallback. Known instances in this codebase:

Auto-Settle loop — DashboardPage.jsx:1424 (this incident) socket GET-back retries, fixed 1s — socketHandlers.js:94-112, 380-434 60s synchronized poll fleet-wide (F3)
