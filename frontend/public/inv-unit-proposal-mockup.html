Investigation 3 — What does the FE send to the backend for drift? API PAYLOAD ANALYSIS
// POST /api/v2/vendoremployee/inventory/add-stock/{itemId}
{
"quantity": 0, // no stock being added — recount only
"unit": "pkt", // item.displayUnit — e.g. "pkt" for ANGARA GREAVY
"physicalqty_master": true, // flags this as a physical count operation
"physical_qty": 4600, // raw user-entered value (gm) — this is what backend uses
"waste_reason": "Select reason...",
"wastage_reason_id": null,
"notes": ""
}
⚠️ Potential mismatch in current payload
unit: "pkt" is sent alongside physical_qty: 4600.

If the backend reads unit to interpret physical_qty, it would see 4600 packets which is wildly wrong.

Owner confirmed the API result is correct, which means the backend likely ignores the unit field for physical_qty and treats it as base units, OR reads the ingredient's own conversion factor from its record.
✅ What Option A fix changes in backend send
Nothing. The drift fix (Option A) only changes the display label shown in the UI.

physical_qty: 4600 still goes to the backend unchanged.

The backend calculates the actual drift internally — the FE never sends a drift field. The FE only sends the user's physical count and the backend does the comparison against its stored quantity.
⚠️ Recommendation before fixing: Verify with backend team whether unit: "pkt" is used to interpret physical_qty or ignored. If it's used, then unit should be changed to item.smallUnit ("gm") in handleSaveAll() as well — otherwise the backend could misread 4600 as 4600 pkt. This is a backend API contract clarification question before any code change.
